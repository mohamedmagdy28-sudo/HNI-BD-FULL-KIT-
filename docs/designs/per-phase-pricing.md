## Problem Statement

User's words: "when i add a program or phase i need to calculate the phase as separate item same table and after i finish the calculation of each phase it calculate the over all of the project." Today the engine pools all phases' costs under ONE proposal markup and allocates the price back proportionally — a phase can never be priced on its own terms, and the phase-by-phase workflow (finish phase 1's number, then phase 2, then read the project total) does not exist.

## Decisions (from the session)

- **D1 — Full chain per phase**: each phase gets its own Markup %, Target margin %, and Price/Day (converters writing back to that phase's canonical markup — the same pattern as the proposal-level chain).
- **D2 — Approach A: default + override.** The existing proposal-level markup stays as the DEFAULT; a phase without its own markup follows it live; a phase with an override owns its price (visible badge + one-click reset). Rejected: B per-phase-only (adds friction to the dominant single-workshop flow), C wizard (ceremony).

## Premises (agreed)

1. Phase price = phase cost × (1 + phase markup); markup canonical per phase, margin/price-day converters.
2. **Gated totaling (protects sent quotes):** with ZERO overrides the engine computes exactly today's chain (one multiplication on pooled cost) — every existing proposal, including SENT/LOCKED ones, reproduces bit-for-bit. The moment ≥1 phase overrides, the project list price becomes the SUM of displayed rounded phase prices (client adding table rows reproduces the total exactly). Per-phase arithmetic is opt-in per proposal, so no stored quote ever drifts on deploy.
3. Discount, VAT, payment schedule stay project-level on the consolidated price. Discount spreading changes basis: proportional to phase LIST SHARES (was cost shares) so a phase's own pricing survives the spread; identical result when no overrides exist.
4. Backward compatible by construction of premise 2's gate: no override → identical numbers, sent-lock guarantee intact.
5. Everything downstream (client doc, PPT, PDF, pipeline revenue/GP, weighted GP, goal band) feeds from the consolidated result with no separate changes.

## Recommended Approach (A: default + override)

**Data model** ([types.ts](../../src/features/pricing/types.ts))
- `Program` gains `markupPct?: number | null` — `null`/absent = inherit the proposal default. `normalizeProposal` backfills nothing (absent IS the inherit state); validates finite ≥ 0 when present.

**Calc engine** ([calc.ts](../../src/features/pricing/calc.ts) — the one real change)
- Per program: `effMarkup_i = program.markupPct ?? proposal.markupPct` (override clamped like the proposal field: `max(0, finite)`; non-finite normalizes to null = inherit, in `normalizeProposal`); `listShare_i = round(cost_i × (1 + effMarkup_i/100))`.
- **Totaling gate (premise 2):** `hasOverrides = programs.some(p => p.markupPct != null)`. Without overrides: `listPrice = round(totalCost × (1 + markupPct/100))` — today's exact formula, and per-phase shares keep coming from allocate as today. With overrides: `listPrice = Σ listShare_i`.
- Discount computes against the consolidated list as today. **The allocate weights are gated exactly like the totaling** (reviewer round-2 catch: per-phase rounding means list shares are NOT exactly cost-proportional, so ungated weights could shift a sent proposal's netShares by a riyal): `netShare_i = allocate(netPrice, weights = hasOverrides ? listShares : costs)` — zero-override mode is today's call bit-for-bit; last-absorbs stays.
- **`listShare_i` is itself gated so chips always sum to the displayed total in BOTH modes**: with overrides `round(cost_i × (1 + effMarkup_i/100))`; without, `allocate(listPrice, costs)_i` (the chips a BD user adds against the summary can never be off by a riyal). Per-program results extend with `listShare_i`, `effMarkupPct_i`, `phaseMarginPct_i = netShare_i > 0 ? (netShare_i − cost_i) / netShare_i : 0` (NET-based, matching the margin block; zero-guarded like the proposal figure), `listPerDay_i = days_i > 0 ? round(listShare_i / days_i) : null`, and `overridden`. The existing `perDay_i` (net-based) remains the CLIENT DOCUMENT's unit-price column only — the two per-day numbers differ on discounted deals by design.
- **Proposal-level `marginPct` formula is UNTOUCHED**: `marginAmount / netPrice` (net-based). Consolidation happens automatically because netPrice and totalCost are sums. The margin block, floor warning, and the pipeline's derived GP (`pipeline.gpPctOverride ?? marginPct`) therefore shift ONLY via premise-2 rounding when overrides exist — never in formula.
- **Phase strip Price/Day**: displays and edits `listPerDay_i` via `markupFromPricePerDay(rate, cost_i, days_i)` per phase (list-based round-trips cleanly; the old net-based value would desync the field on discounted deals). Strip fully disabled when `cost_i === 0` (no override creatable; an existing override still shown + resettable) — the per-phase analogue of `pricingDisabled`.
- **SummaryPanel Price/Day knob under overrides**: a NEW `CalcResult.defaultPricePerDay` — `round(Σ listShare_inheriting / Σ days_inheriting)`, null when no inheriting phase has days — is what the knob displays; `markupFromPricePerDay` runs on inheriting cost/days so the typed rate round-trips for the phases the knob controls. `result.pricePerDay` keeps its consolidated meaning untouched for any other consumer. All phases overridden → knob disabled with an i18n hint ("all phases set their own price").
- **markSent snapshot note**: none needed — the gate keeps sent proposals' math frozen as long as their programs carry no overrides, and an override added AFTER sending is impossible (quote fields are sent-locked).

**UI** ([CostTable.tsx](../../src/features/pricing/CostTable.tsx) program card + [SummaryPanel.tsx](../../src/features/pricing/SummaryPanel.tsx))
- Each program card's footer gains a compact pricing strip: Markup % | Target margin % | Price/Day (MoneyInput, grouped) | live chip "Price {money(listShare_i)} · Margin {phaseMarginPct_i}%" (price = the phase's pre-discount set price; margin = net-based, matching the margin block). All three write to that phase's markup via the existing converters; the price/day and target-margin inputs reuse the draft-while-focused pattern (no controlled-input hijack).
- Inherit state: inputs show the inherited value as placeholder (grey), like the pipeline GP% pattern; typing creates the override; an "override" badge (StatusBadge, neutral) + X-reset appears when set; reset returns the phase to following the default.
- SummaryPanel: markup/target-margin/price-day knobs remain and edit the DEFAULT; when ≥1 phase overrides, a one-line note under the knobs: "Applies to N of M phases" (i18n EN/AR). Margin block = consolidated. A per-phase mini-table is NOT added to the summary (the phase cards carry it — same table, as the user asked).
- Sent-lock disables the phase strips like every quote field.

**Explicitly unchanged**: client document layout (per-phase investment rows now show each phase's own price via netShare), unit-price/day column, PPT/PDF export, pipeline flows, schedule, VAT.

**Tests**
- Unit (calc): override changes only its phase; inherit tracks default edits; converter round-trips per phase; **rounding invariant scoped per mode** — override mode: Σ listShare_i = listPrice exactly by construction; gated mode: allocate guarantees Σ = listPrice; both asserted. Discount spread proportional to the gated weights; margin consolidation via untouched net formula.
- Existing calc fixtures: ALL pass unchanged (the totaling gate guarantees it — every fixture has zero overrides). The new suite MUST add an unequal-cost multi-phase fixture WITH overrides where Σ round(c_i·k_i) ≠ round(Σ…) to prove the summed totaling is actually exercised, plus a zero-override multi-phase fixture asserting bit-identical totals with today's formula.
- e2e: two-phase proposal — set phase 2 override 60%, phase 1 inherits; assert phase chips, consolidated margin block, client doc rows sum to total; reset-to-default restores; EN/AR.

## Not in scope

- Per-phase discounts, VAT, or payment schedules (project-level by premise 3).
- Per-phase pricing in the PIPELINE table (deal level stays consolidated).
- Reordering phases, phase templates, or copying pricing between phases.
- Duplicate (V0.2) COPIES phase overrides with the programs — deliberate: a revision starts from the same pricing.

## Success Criteria

- Price a 3-phase deal with three different margins; each phase card shows its own price and margin; the summary shows the consolidated figures; the client document's phase rows sum exactly to the printed total.
- A single-phase workshop priced before and after this change shows identical numbers.
- Full DoD: 4 breakpoints × EN/AR, judge-clean states, existing suite green UNCHANGED (the gates guarantee it); the two new mandated fixtures added: unequal-cost WITH overrides (proves summed totaling), unequal-cost WITHOUT overrides (proves bit-identical totals AND netShares vs today's formula).
