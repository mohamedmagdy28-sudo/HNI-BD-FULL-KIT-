## Problem Statement

Every proposal the calculator produces must also be entered, by hand, into the team's Google Sheets pipeline, and the BD lead has no live answer to "how much have I achieved so far, and what is in the pipeline in revenue and GP". Add a Pipeline tab that carries the sheet's exact columns, auto-fills everything the app already knows, lets the user fill the judgment fields (stage, winning probability), computes an achievement dashboard, and exports rows for pasting into the sheet.

## Demand Evidence and Status Quo

- Double entry today: proposal built in the app, then retyped into the pipeline sheet. GP% and GP amount are computed by the app and retyped as static values.
- The user supplied the sheet's real header row (19 columns) and stage taxonomy (Proposal, Initial Negotiation, Final Negotiation, Verbal Awarding, Won, Lost) on request: the design maps to reality, not an idealized CRM.
- Probe evidence: the sheet is private (HTTP 401 on anonymous CSV export), so the public serverless app can never touch it directly.

## Premises (as revised during the session)

1. REVISED (user decision, supersedes the mirror/Apps-Script plan): the Google Sheet is a SEPARATE ENTITY. The app never reads or writes it. The Pipeline tab mirrors the sheet's headers; the user fills stage/probability in the app, then moves rows out via copy-paste or CSV and pastes into the sheet themselves.
2. The app is the source of truth for its own dashboard; imported external deals (approach C) cover history that predates the app.
3. Proposals gain pipeline fields; Stage uses the sheet's six values. Won = achieved; Lost = excluded; the other four stages = open pipeline.
4. "Achieved so far" is shown against user-set period targets (revenue and GP, with a period start/end) in Settings; per-deal Target Achievement Contribution % derives from the revenue target.
5. (D4-C) All exported values stay SAR; the sheet's Currency column records SAR; any AED conversion happens inside the sheet, owned by the user.

## Recommended Approach (C)

### Data model

- `Proposal.pipeline` (all optional; a proposal enters the pipeline when the user first sets any pipeline field, typically at Mark-as-sent time): `source`, `dealType`, `sector`, `primaryService` (free text with remembered suggestions from prior entries), `stage` (enum of the six sheet values), `winningProbability` (integer percent), `deliveryStart`, `deliveryEnd` (ISO dates), `poNumber`, `projectStatus` (free text), `notes`, and `decidedAt` (ISO date, auto-stamped when stage changes to Won or Lost, editable afterwards; it drives the achieved-in-period calculation).
- SENT-LOCK EXEMPTION, explicit amendment to the parent design: pricing-costing-calculator.md states a sent proposal "can never change"; that guarantee is hereby narrowed to the QUOTED DOCUMENT's fields (client, programs, cost lines, pricing, schedule). Pipeline fields are sales-journey state, not quote content, and stay editable after Mark-as-sent. The existing lock tests (store and E2E) are amended in the same change to assert the narrowed rule.
- Schema drift: `normalizeProposal` backfills `pipeline` (undefined -> {}) per the repo's established pattern; the ExternalDeal store follows the same corrupt-key tolerance as proposals.
- `ExternalDeal`: imported sheet rows that have no app proposal. Same shape as a pipeline row (all 19 columns as stored strings/numbers) plus `id` and `importedAt`. Stored under `hni.pricing.v1.external.<id>` with an index key, behind the same PricingStore interface.
- `Settings` gains `targets: { periodStart, periodEnd, revenueTarget, gpTarget }` and nothing else (no script URLs: there is no integration).

(AED)` 17. `Traget Achivement Contribution %` 18. `Project Status` 19. `Notes`

Stage is STORED and EXPORTED as the sheet's exact English strings (Proposal, Initial Negotiation, Final Negotiation, Verbal Awarding, Won, Lost) so the sheet's dropdown validation keeps working; the UI merely displays localized labels.

### Pipeline tab (third header mode, alongside Documents; router still deferred per CLAUDE.md until a true second route exists)

- KPI strip (existing KpiStrip component): Achieved Revenue (Won, within period) with % of target, Achieved GP with % of target, Open Pipeline (count + revenue), Weighted Pipeline (sum of value x probability over open stages). Semantic colors; magenta only for emphasis per brand rules.
- Table beneath in sheet column order: app proposals (linked, click opens the proposal) and imported external deals, stage editable inline, chips for stage, sync-free.
- Row actions: none destructive beyond existing proposal delete; external deals deletable.
- Empty state, target-not-set state (KPIs show totals with a "set targets" nudge), EN/AR first-class, logical utilities, tabular numerals.

### Export

- "Copy rows" puts rows on the clipboard as TSV in exact sheet column order: pasting into Google Sheets fills the 19 columns cleanly. DEFAULT SELECTION: app proposals only; imported ExternalDeals already live in the sheet and exporting them by default would paste duplicates. A source filter (app / imported / all) covers the exceptions. Resolves the old "Copy-as-formatted-table" TODO pattern for this surface.
- "Download CSV" with the same columns and default for the Excel route the user described.
- Escaping: TSV cell values have tabs and newlines replaced with single spaces (a multi-line note must not shear the paste grid); CSV fields are double-quoted with internal quotes doubled per RFC 4180.
- Both exports are client-facing-safe by definition (the pipeline sheet is internal; GP columns are intended there).

### Import (one-time backfill, repeatable safely)

- User downloads the sheet tab as CSV and drops it on the Pipeline tab.
- Parser maps by header names (tolerant of column reordering; unknown columns are ignored with a report). Rows become ExternalDeals. Dedup: a row whose Company+Project Name matches an existing app proposal (trimmed, case-insensitive) is NOT dropped; instead its manual pipeline fields (stage, probability, dates, PO, status, notes, source, type, sector, service) seed that proposal's empty pipeline fields, and the match is reported. Nothing is silently undercounted.
- Numbers parsed leniently (currency symbols, commas stripped); a row whose value or GP cell stays unparseable is EXCLUDED from dashboard sums, counted in a visible "N rows excluded from totals" note on the KPI strip, and kept in the table flagged for manual correction.
- Re-import replaces all ExternalDeals (import is a snapshot refresh, mirroring JSON import semantics), never overwrites app proposal fields (dedup seeding fills empty pipeline fields only, so re-import is idempotent).

### Dashboard math

- Achieved: stage = Won AND (decided date, defaulting to proposal date for imports, within the target period when targets are set; all-time otherwise). Won requires setting `decidedAt` (auto-stamped when stage changes to Won or Lost, editable).
- Open pipeline: stages Proposal, Initial Negotiation, Final Negotiation, Verbal Awarding.
- Weighted pipeline: sum(net value x winningProbability/100) over open stages; rows without probability count at 0 and are flagged in the tab.
- All rounded-canonical whole SAR, consistent with the calculator.

## Eng Review Amendments (2026-08-31, all user-approved)

- (1A) Editing surface: stage and winning probability inline in the table; all other pipeline fields in a per-row drawer using the existing DetailSheet component. External deals use the same drawer (their fields are the 19 columns directly).
- (2A) Import parser: hand-rolled RFC 4180 (quoted commas, embedded newlines, doubled quotes), no new dependency, tested against a real-sheet fixture.
- (3A) Imported dates: ISO and unambiguous formats parse; ambiguous day/month strings read as DD/MM/YYYY (declared Gulf convention); unparseable dates flag the row out of period math via the visible excluded-rows note.
- (T1) IMPORT SIMPLIFIED, supersedes the dedup-seeding design: import is a one-time backfill; ALL rows become external deals; rows matching an app proposal (trim/case-insensitive company+project) are only REPORTED as possible duplicates for the user to delete on either side; nothing ever writes into app proposals; re-import warns it replaces external deals including manual corrections. The reconciliation success criterion becomes: after import and duplicate cleanup, dashboard totals match the sheet's sums.
- (T2) Copy rows stamps each exported row (copiedAt vs updatedAt); the default selection is new-or-changed-since-last-copy; an all-rows option remains for full rebuilds.
- (T3.1) Currency column validated on import: non-SAR rows excluded from sums and counted in the excluded note.
- (T3.2) Imported Won deals with a defaulted decision date are flagged (quarter attribution is a guess).
- (T3.3) decidedAt lifecycle: reverting to an open stage clears it; auto-stamp never overwrites a manually edited date. Covered by tests.
- (T3.4) Sent-lock narrowing enforced structurally: a dedicated updatePipeline(id, fields) write path that cannot express quote-field changes; regression tests assert both directions.
- (T3.5) JSON backup payload v2: includes external deals and targets; import replaces external keys too; v1 payloads still import.
- (T3.6) Pipeline membership predicate: stage is set. Stage-less proposals do not export, count, or appear as pipeline rows; the sheet's Stage validation never receives an empty cell.
- (T3.7) Deleting a Won/Lost-staged proposal asks one confirmation (deliberate, narrow exception to the accepted no-confirm decision: the delete now mutates reported business numbers).
- (T3.8) The weighted-pipeline KPI shows a companion "N deals unweighted" count; missing probability is visible, not silently zero.
- BUILD GATE (from outside-voice findings 4, 8, 9, 14): before implementation, the user provides one CSV export of the pipeline tab (values may be anonymized, formats must be real). It answers: how Winning Probability / GP% / Contribution cells are formatted (50 vs 50% vs 0.5), the export date format the sheet expects, whether Source / Deal Type / Sector / Primary Service carry dropdown validation, and whether any historical rows are non-SAR. It doubles as the parser test fixture.

## BUILD AMENDMENTS (2026-08-31, during implementation)

1. **Pipeline entry point.** The approved design defined membership (in pipeline iff stage set) but no control that sets the FIRST stage: the pipeline table lists only in-pipeline proposals, so nothing could ever enter it. Added a Stage select to the proposal edit header (testid `pipeline-stage-edit`), never disabled by the sent-lock, writing through the structural `updatePipeline` path with the same auto-decidedAt stamping as the table's stage select. A "No stage" item removes the proposal from the pipeline and clears decidedAt.
2. **KpiStrip columns.** The shared strip was fixed at lg:grid-cols-6; four pipeline tiles left two dead gray cells. The component now derives wide-breakpoint columns from the tile count (and drops md:grid-cols-3 when the count is not divisible by 3, so 4 tiles render 2x2 on tablets).
3. **Build gate defaults live in code.** The waived CSV gate's format unknowns are isolated as constants documented at the top of `pipelineCsv.ts` (percents "50%", plain integer money, DD/MM dates). Tune after the first real paste test.

Verified: 88 unit tests, 176 e2e (22 tests x 8 viewport/language projects), visual check EN LTR + AR RTL.

## AMENDMENT: direct .xlsx import (2026-08-31)

User request: upload the pipeline sheet as an Excel file instead of CSV. Added `src/features/pricing/xlsx.ts`, a minimal first-worksheet reader built on JSZip (already in the tree; promoted from devDependencies, loaded lazily so it stays out of the main bundle). It converts typed cells to the exact grid strings the shared `parsePipelineRows` parser expects: date-styled serials become ISO dates, percent-styled fractions become "50%", numbers stay plain. This sidesteps the CSV format-guessing for import entirely; the export-side defaults still need the first real paste test. The import button accepts both formats and branches on the ZIP magic bytes, so a renamed file still imports. Dev note: `optimizeDeps.include: ["jszip"]` prevents a Vite dev full-page reload on first lazy load.
