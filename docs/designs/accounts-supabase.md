## Problem Statement

"Set user name and password for the app." Diagnostic pinned the real requirement: **colleagues with their own accounts** (D1), with **own proposals private + one shared team pipeline** (D2). A static client cannot fake this — real auth requires the backend the repo reserved from day one (`PricingStore` interface, documented Supabase triggers).

## Decisions (from the session)

- **D1 — Threat model: real multi-user accounts**, not a client-side gate (rejected as security theater: any bundle-embedded check is bypassable and protects no data).
- **D2 — Sharing shape: own proposals private, pipeline shared.** Colleagues see deal revenue/GP in the pipeline without opening the owner's costing.
- **D3 — Approach A: full Supabase store.** Rejected: B local-first sync (XL, conflict hell — later evolution at most), C pipeline-only wedge (leaves proposals trapped per laptop, undercutting the login's point).
- **Premise 4 accepted:** the web app with accounts is the team's primary surface; the approved desktop packaging is postponed to a later personal offline edition.

## Premises (agreed)

1. Supabase, invite-only email+password. No open signup; the owner creates colleague accounts in the dashboard.
2. Data moves to Supabase Postgres (nearest region) under row-level security — a named reversal of "data never leaves the browser". Export-backup remains the escape hatch. Signature/stamp images stay data URLs inside per-user `user_settings` rows protected by RLS (not Supabase Storage buckets) — still never in the public bundle, now also safe from laptop theft.
3. Proposals/costing: private per owner. Pipeline (rows, imported externals, targets, goal band): team-shared.
4. Anon key + URL ship in the bundle by design (Supabase's model); security lives in RLS policies, not key secrecy.

## Recommended Approach (A: Full Supabase store)

**The load-bearing data-model decision (resolves shadow-clobbering):** sales-journey fields — stage, probability, decidedAt, source, dealType, sector, primaryService, delivery dates, PO, projectStatus, notes — become **canonical on `pipeline_rows` for everyone, including the owner**. `proposals.data` keeps quote content only (client, title, costing, schedule, sentAt). The owner's autosave upserts ONLY identity+money columns (client, title, value, gp_amount, gp_pct) and never touches journey columns after the initial insert, so a teammate's stage edit can never be clobbered by the owner's next save. `buildRows` reads journey fields from `pipeline_rows` for own rows too; teammates' rows render like externals (value/GP visible, no "View costing").

**Client**
- **`PricingStore` interface v2 (enumerated — the abstraction that keeps one in-memory model across both modes):** at load, `SupabaseStore` hydrates each own proposal's `.pipeline` from its `pipeline_rows` row, so the in-memory `Proposal` shape is IDENTICAL in both modes and calc/UI code never branches. Changes: `loadAll(): Promise<LoadResult>` with `LoadResult` gaining `teamRows: TeamPipelineRow[]` (teammates' rows, rendered as pseudo-externals); `saveProposal(p, order)` strips journey fields from `data` and upserts identity+money columns; new `updateJourney(proposalId, patch: Partial<PipelineInfo>)` replaces the screen's direct pipeline write — cloud: UPDATE journey columns (or DELETE the row when the patch clears the stage); local: merge into `proposal.pipeline` as today; new `updateTeamJourney(rowId, patch)` for teammates' rows (local mode: no-op); `stampCopied(ids)` writes the `copies` table (local: copiedAt as today). `gpPctOverride` stays owner-private inside `proposals.data` and feeds the gp columns the owner upserts — it is neither a journey column nor team-editable.
- `SupabaseStore implements PricingStore` beside `LocalStoragePricingStore`. Boot: env vars present → auth gate → async `loadAll` behind a branded loading screen → render; env absent → localStorage mode exactly as today (dev, unit tests, and the Playwright matrix run against this mode and MUST stay green — boot becomes async in both modes, so "green" is the criterion, not "untouched").
- **Write path (resolves async-ordering)**: per-record single-flight write queues — one chain per proposal/row id, latest-state coalescing, in-order dispatch; optimistic UI with a subtle saving/saved indicator in the header. Keepalive is used ONLY for the unload-time flush and only when the request body is under ~60KB (browsers cap keepalive bodies at ~64KB — proposals with client logos and signature settings routinely exceed it, so a blanket keepalive fetch would make the biggest saves always fail); everything else uses normal fetch, and `beforeunload` warns whenever any queue is non-empty.
- **Session expiry**: supabase-js auto-refresh on; on a hard 401 the queues pause and a re-login modal appears preserving all in-memory state; queues resume after sign-in. The storage-error banner remains quota/network-only.
- **Freshness/conflicts**: shared data (pipeline_rows, external_deals, team_settings) re-fetches after each own write and on tab focus; conflict policy is last-write-wins per row (DB `updated_at` trigger), and the refresh merge skips any row whose input currently has focus so typing is never discarded.
- Auth UI: login screen (email+password, sign-out in header), EN/AR RTL, tokens; no self-serve signup/reset v1 (owner manages via dashboard; **email confirmation must be disabled in Supabase auth settings** or owner-created accounts cannot log in).
- New dependency: `@supabase/supabase-js` only.

**Schema (committed SQL migration, run once in the dashboard)**
- `proposals(id uuid pk, owner uuid not null default auth.uid() references auth.users on delete cascade, data jsonb, sort_index int, updated_at)` — RLS: owner-only CRUD (`USING owner = auth.uid()` + `WITH CHECK` same); display order via `sort_index`.
- `pipeline_rows(proposal_id uuid pk references proposals(id) on delete cascade, owner uuid not null default auth.uid(), client text, title text, value bigint, gp_amount bigint, gp_pct numeric, stage text, probability int, decided_at date, source text, deal_type text, sector text, primary_service text, delivery_start text, delivery_end text, po_number text, project_status text, notes text, updated_at)` — RLS: authenticated SELECT all; INSERT `WITH CHECK (owner = auth.uid())`; UPDATE allowed to all authenticated **but** a `BEFORE UPDATE` trigger raises when `owner` or `proposal_id` change at all (by anyone), and when `auth.uid() <> owner` AND any of (client, title, value, gp_amount, gp_pct) changed — journey columns are team-editable, identity/money are owner-only (this trigger is the enforcement mechanism; Postgres has no column-level RLS). DELETE: owner only; the client also deletes the row explicitly when the owner clears the stage (membership rule), and the FK cascade covers proposal deletion — no ghost rows.
- `external_deals(id uuid pk, data jsonb, updated_at)` — team CRUD. **Re-import in cloud mode is a team-visible replace**: the existing confirm dialog text gains "for the whole team".
- `team_settings(id smallint pk, targets jsonb)` — **seeded with row 1 by the migration**; clients UPDATE only.
- `user_settings(user_id uuid pk default auth.uid(), data jsonb)` — marginFloorPct, lastExportAt, signature/stamp data URLs; owner-only RLS. Client-side `Settings` maps: targets ← team_settings; everything else ← user_settings; `saveSettings` fans out to the changed table(s).
- Every policy denies `anon`.

**Copy-rows under sharing (resolves copiedAt)**: per-user stamps in `copies(user_id, row_id, copied_at, pk(user_id,row_id))`, RLS `user_id = auth.uid()` for all operations; "copy new" = rows without MY stamp; a colleague's copy never marks rows copied for me. No FK on `row_id` (it spans pipeline_rows and external_deals) — orphan stamps after deletes are harmless, and an external re-import (new ids) resets everyone's new-since-last-copy, accepted. Sheet export itself is unchanged. **Mark-as-sent ordering**: insert the `pipeline_rows` row FIRST, then update `proposals.data`; on partial failure `loadAll` reconciles (an in-pipeline proposal without a row gets re-inserted), so a sent proposal can never stay invisible to the team.

**Export/Import in cloud mode**: Export backup stays (full snapshot of what I can see). The Import button is repurposed: it restores OWN proposals + user settings only and never touches team-shared tables; the one-time migration prompt (first login with zero cloud proposals AND local data present) is the only flow that also offers pushing this browser's externals/targets to the team — skipped with a notice if the team tables are already populated (first importer wins).

**corruptIds in cloud mode**: rows whose jsonb fails `normalizeProposal` parse are skipped and surfaced through the existing corrupt-data banner, same as localStorage.

## Not in scope

- Roles/permissions beyond owner-vs-team (no admin UI, no per-deal ACLs).
- Offboarding beyond the dashboard: deleting an auth user cascades away their proposals and pipeline rows by design; archiving a leaver's book is a future feature (export their backup first).
- Password reset flows, SSO, MFA (dashboard-managed v1).
- Offline mode / local-first sync (approach B — only as a future evolution).
- The desktop packaging build (postponed by premise 4; design doc stays approved).
- Realtime live cursors/presence.

## Success Criteria

- Two real accounts on separate machines: each sees only their own proposals; both see and can update one shared pipeline (stage/probability), and the goal band reflects the combined team book.
- A colleague CANNOT read another's proposal via the API even with devtools (adversarial test with the bare anon key), CANNOT insert a pipeline row owned by someone else, CANNOT change value/GP on another's row, and CANNOT reassign a row's `owner` via UPDATE (trigger tests).
- A teammate's stage edit SURVIVES the owner's next proposal autosave (the clobber test — the reason journey fields are canonical on the shared row).
- Closing the tab immediately after an edit does not lose it (keepalive write or unload warning).
- Existing browser data lands in the owner's account via the migration prompt with identical totals (the import splits each local proposal into journey-stripped `proposals.data` + a `pipeline_rows` insert; getting this wrong would silently drop the whole imported pipeline).
- localStorage mode still fully green: unit suite + entire Playwright matrix pass (boot is async in both modes; green is the criterion).
- Login, loading, and error states pass EN/AR at the four breakpoints (existing DoD).
