## Problem Statement

"Set user name and password for the app." Diagnostic pinned the real requirement: **colleagues with their own accounts** (D1), with **own proposals private + one shared team pipeline** (D2 — since REVERSED, see Decisions: v1 is team-readable, owner-writable). A static client cannot fake this — real auth requires the backend the repo reserved from day one (`PricingStore` interface, documented Supabase triggers).

## Decisions (from the session)

- **D1 — Threat model: real multi-user accounts**, not a client-side gate (rejected as security theater: any bundle-embedded check is bypassable and protects no data).
- **D2 (REVERSED 2026-09-02) — Sharing shape: ALL proposals team-readable, owner-writable.** Original decision was own-proposals-private + shared pipeline. The user's country-manager requirement ("I will need to see the proposals of the whole team") plus his explicit choice of symmetric visibility for the two-person v1 (him + Heba) replace it: every account READS every proposal (drafts included, full costing, documents, costing Excel); every account WRITES only its own. A manager/member role model (profiles.role + is_manager() RLS) was designed, second-opinion-reviewed, and DEFERRED — the v1 choice was symmetric on purpose; roles-v2 is a policy tightening, not a rebuild.
- **D3 — Approach A: full Supabase store.** Rejected: B local-first sync (XL, conflict hell — later evolution at most), C pipeline-only wedge (leaves proposals trapped per laptop, undercutting the login's point).
- **Premise 4 accepted:** the web app with accounts is the team's primary surface; the approved desktop packaging is postponed to a later personal offline edition.

## Premises (agreed)

1. Supabase, invite-only email+password. No open signup; the owner creates colleague accounts in the dashboard.
2. Data moves to Supabase Postgres (nearest region) under row-level security — a named reversal of "data never leaves the browser". Export-backup remains the escape hatch. Signature/stamp images stay data URLs inside per-user `user_settings` rows protected by RLS (not Supabase Storage buckets) — still never in the public bundle, now also safe from laptop theft.
3. (REVISED) Proposals/costing: team-READABLE, owner-writable. Pipeline (rows, imported externals, targets, goal band): team-shared as before. Signature/stamp images stay strictly per-user (user_settings, owner-only RLS) — a teammate's document view renders from proposal data and shows signature blocks blank.
4. Anon key + URL ship in the bundle by design (Supabase's model); security lives in RLS policies, not key secrecy.

## Recommended Approach (A: Full Supabase store)

**The load-bearing data-model decision (resolves shadow-clobbering):** sales-journey fields — stage, probability, decidedAt, source, dealType, sector, primaryService, delivery dates, PO, projectStatus, notes — become **canonical on `pipeline_rows` for everyone, including the owner**. `proposals.data` keeps quote content only (client, title, costing, schedule, sentAt). The owner's autosave upserts ONLY identity+money columns (client, title, value, gp_amount, gp_pct) and never touches journey columns after the initial insert, so a teammate's stage edit can never be clobbered by the owner's next save. `buildRows` reads journey fields from `pipeline_rows` for own rows too; teammates' rows render like externals with a "View proposal" action linking (via `proposal_id`) to the read-only team-proposal view — under reversed D2 the costing is readable anyway, so hiding the link would be a navigation gap, not a privacy boundary.

**Team visibility (amendment, 2026-09-02)**
- `LoadResult` gains `teamProposals: Array<{ proposal: Proposal; ownerId: string; ownerName: string }>` — everyone else's proposals. `LocalStoragePricingStore` returns `[]`, hardcoded; local mode unchanged.
- **The separation rule (adversarial-review catch, adopted):** `teamProposals` is a SEPARATE render surface. It is never merged into `proposals` and never fed to `buildRows` or any pipeline/goal-band math — teammates' deals already arrive through the shared `pipeline_rows` channel, and merging would double-count every sent deal and leak drafts into totals. Mandatory test: with Heba owning one sent 100K deal, Mohamed's pipeline reads 100K (not 200K) and her drafts never appear in the goal band.
- **UI:** a "Team proposals" section in the proposal list, grouped by owner with name badge and draft/sent indicator. Opening one reuses the sent-lock read-only RENDERING but the lock is KEYED ON OWNERSHIP (`owner !== session user`), never on `sentAt` (drafts have `sentAt = null`). Consistent with the sent-lock philosophy, the QUOTE is read-only while the sales-journey panel stays editable, routing through `updateTeamJourney` (journey columns are team-editable by schema design). Banner wording: "Quote read-only — owned by {name}. Pipeline fields stay team-editable." The autosave debounce is NOT REGISTERED for a proposal whose owner is not the session user (a fired autosave would 403 and poison the write queue; any 403 that still occurs surfaces loudly, never retried). Client documents and the costing Excel download work on the loaded read-only proposal; signature/stamp blocks render blank (owner-only settings).
- **No new write methods on PricingStore** — read-only-by-construction beats read-only-by-guard.
- New i18n keys EN/AR: teamProposals, readOnlyOwnedBy, ownerless fallback.

**Client**
- **`PricingStore` interface v2 (enumerated — the abstraction that keeps one in-memory model across both modes):** at load, `SupabaseStore` hydrates each own proposal's `.pipeline` from its `pipeline_rows` row, so the in-memory `Proposal` shape is IDENTICAL in both modes and calc/UI code never branches. Changes: `loadAll(): Promise<LoadResult>` with `LoadResult` gaining `teamRows: TeamPipelineRow[]` (teammates' rows, rendered as pseudo-externals); `saveProposal(p, order)` strips journey fields from `data` and upserts identity+money columns; new `updateJourney(proposalId, patch: Partial<PipelineInfo>)` replaces the screen's direct pipeline write — cloud: UPDATE journey columns (or DELETE the row when the patch clears the stage); local: merge into `proposal.pipeline` as today; new `updateTeamJourney(rowId, patch)` for teammates' rows (local mode: no-op); `stampCopied(ids)` writes the `copies` table (local: copiedAt as today). `gpPctOverride` stays owner-private inside `proposals.data` and feeds the gp columns the owner upserts — it is neither a journey column nor team-editable.
- `SupabaseStore implements PricingStore` beside `LocalStoragePricingStore`. Boot: env vars present → auth gate → async `loadAll` behind a branded loading screen → render; env absent → localStorage mode exactly as today (dev, unit tests, and the Playwright matrix run against this mode and MUST stay green — boot becomes async in both modes, so "green" is the criterion, not "untouched").
- **Write path (resolves async-ordering)**: per-record single-flight write queues — one chain per proposal/row id, latest-state coalescing, in-order dispatch; optimistic UI with a subtle saving/saved indicator in the header. Keepalive is used ONLY for the unload-time flush and only when the request body is under ~60KB (browsers cap keepalive bodies at ~64KB — proposals with client logos and signature settings routinely exceed it, so a blanket keepalive fetch would make the biggest saves always fail); everything else uses normal fetch, and `beforeunload` warns whenever any queue is non-empty.
- **Session expiry**: supabase-js auto-refresh on; on a hard 401 the queues pause and a re-login modal appears preserving all in-memory state; queues resume after sign-in. The storage-error banner remains quota/network-only.
- **Freshness/conflicts**: shared data (pipeline_rows, external_deals, team_settings) re-fetches after each own write and on tab focus; conflict policy is last-write-wins per row (DB `updated_at` trigger), and the refresh merge skips any row whose input currently has focus so typing is never discarded. `teamProposals` joins the tab-focus re-fetch list AND re-fetches on opening a team proposal, so the review surface is never a session stale.
- Auth UI: login screen (email+password, sign-out in header), EN/AR RTL, tokens; no self-serve signup/reset v1 (owner manages via dashboard; **email confirmation must be disabled in Supabase auth settings** or owner-created accounts cannot log in).
- New dependency: `@supabase/supabase-js` only.

**Schema (committed SQL migration, run once in the dashboard)**
- `proposals(id uuid pk, owner uuid not null default auth.uid() references auth.users on delete cascade, data jsonb, sort_index int, updated_at)` — RLS as SPLIT PER-COMMAND policies (never FOR ALL; write-denial is grammar, not a condition someone might edit): `SELECT` for all authenticated; `INSERT`/`UPDATE`/`DELETE` `USING/WITH CHECK owner = auth.uid()`. Display order via `sort_index` (per-owner meaning only).
- `profiles(id uuid pk references auth.users on delete cascade, display_name text)` — names ONLY, no role column in v1. SELECT for all authenticated; NO client INSERT/UPDATE policies (dashboard-seeded when creating each account). Labels teammates' proposals and pipeline rows; auth.users is not client-readable, so this table is the only name source.
- `pipeline_rows(proposal_id uuid pk references proposals(id) on delete cascade, owner uuid not null default auth.uid(), client text, title text, value bigint, gp_amount bigint, gp_pct numeric, stage text, probability int, decided_at date, source text, deal_type text, sector text, primary_service text, delivery_start text, delivery_end text, po_number text, project_status text, notes text, updated_at)` — RLS: authenticated SELECT all; INSERT `WITH CHECK (owner = auth.uid())`; UPDATE allowed to all authenticated **but** a `BEFORE UPDATE` trigger raises when `owner` or `proposal_id` change at all (by anyone), and when `auth.uid() <> owner` AND any of (client, title, value, gp_amount, gp_pct) changed — journey columns are team-editable, identity/money are owner-only (this trigger is the enforcement mechanism; Postgres has no column-level RLS). DELETE: owner only; the client also deletes the row explicitly when the owner clears the stage (membership rule), and the FK cascade covers proposal deletion — no ghost rows.
- `external_deals(id uuid pk, data jsonb, updated_at)` — team CRUD. **Re-import in cloud mode is a team-visible replace**: the existing confirm dialog text gains "for the whole team".
- `team_settings(id smallint pk, targets jsonb)` — **seeded with row 1 by the migration**; clients UPDATE only.
- `user_settings(user_id uuid pk default auth.uid(), data jsonb)` — marginFloorPct, lastExportAt, signature/stamp data URLs; owner-only RLS. Client-side `Settings` maps: targets ← team_settings; everything else ← user_settings; `saveSettings` fans out to the changed table(s).
- Every policy denies `anon`.

**Copy-rows under sharing (resolves copiedAt)**: per-user stamps in `copies(user_id, row_id, copied_at, pk(user_id,row_id))`, RLS `user_id = auth.uid()` for all operations; "copy new" = rows without MY stamp; a colleague's copy never marks rows copied for me. No FK on `row_id` (it spans pipeline_rows and external_deals) — orphan stamps after deletes are harmless, and an external re-import (new ids) resets everyone's new-since-last-copy, accepted. Sheet export itself is unchanged. **Mark-as-sent ordering**: insert the `pipeline_rows` row FIRST, then update `proposals.data`; on partial failure `loadAll` reconciles (an in-pipeline proposal without a row gets re-inserted), so a sent proposal can never stay invisible to the team.

**Export/Import in cloud mode**: Export backup stays (full snapshot of what I can see), with the payload gaining owner tags: own proposals in the existing field, teammates' in a separate `teamProposals` section. The Import button is repurposed: it restores ONLY the own-proposals section + user settings (the team section is backup-for-reading, never imported — importing it would resurrect teammates' proposals under the importer's account) and never touches team-shared tables; the one-time migration prompt (first login with zero cloud proposals AND local data present) is the only flow that also offers pushing this browser's externals/targets to the team — skipped with a notice if the team tables are already populated (first importer wins).

**corruptIds in cloud mode**: rows whose jsonb fails `normalizeProposal` parse are skipped and surfaced through the existing corrupt-data banner, same as localStorage.

## Success Criteria

- Two real accounts (Mohamed + Heba) on separate machines: each sees BOTH proposal books (own editable, teammate's read-only with owner banner); both see and can update one shared pipeline (stage/probability), and the goal band reflects the combined team book.
- The double-count test: Heba owns one sent 100K deal; Mohamed's pipeline total reads 100K, and her unsent drafts never appear in his goal band or deal counts.
- Write-denial test: Heba's session attempts UPDATE/DELETE on Mohamed's proposal with the bare anon key — refused by RLS; her UI never fires an autosave on his proposals.
- A colleague CANNOT write another's proposal via the API even with devtools (reads are team-wide by design), CANNOT insert a pipeline row owned by someone else, CANNOT change value/GP on another's row, and CANNOT reassign a row's `owner` via UPDATE (trigger tests). user_settings (signatures/stamps) remain unreadable across accounts.
- A teammate's stage edit SURVIVES the owner's next proposal autosave (the clobber test — the reason journey fields are canonical on the shared row).
- Closing the tab immediately after an edit does not lose it (keepalive write or unload warning).
- Existing browser data lands in the owner's account via the migration prompt with identical totals (the import splits each local proposal into journey-stripped `proposals.data` + a `pipeline_rows` insert; getting this wrong would silently drop the whole imported pipeline).
- localStorage mode still fully green: unit suite + entire Playwright matrix pass (boot is async in both modes; green is the criterion).
- Login, loading, and error states pass EN/AR at the four breakpoints (existing DoD).
