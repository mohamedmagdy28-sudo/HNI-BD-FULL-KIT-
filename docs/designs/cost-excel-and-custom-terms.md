## Problem Statement

User's words: "1. Export Cost of the project / Program into excel and record it in the documents as excel. 2. use the standard terms and conditions as button or customized terms and conditions with big text box to add customized terms and conditions as text and it will follow the branding and format and it will replace the standard terms and conditions."

Two gaps in the deal workflow today: the internal costing behind a quote cannot leave the app as a working Excel file, and any negotiated change to the legal terms forces hand-editing the exported PowerPoint outside the app.

## Demand Evidence

The requester is the daily user; both features come from live deals in his pipeline. The Documents tab already exists precisely because he re-opens quoted deals later; this extends that archive with the internal economics and the negotiated legal text.

## Decisions (from the session)

- **D1 — Internal costing workbook.** The Excel contains the full internal picture: every cost line (qty, rate, subtotal) per phase, phase totals, effective markup, phase price, phase margin, discount, VAT, grand total. It is for HNI eyes only. Rejected: client-safe price sheet (too thin for the stated job), both-tabs-in-one-file (one wrong forward emails margins to a client).
- **D2 — Editor + Documents row.** Download button in the proposal editor (drafts included) AND an action on each Documents row. The file regenerates from proposal data on every click; no file bytes are ever stored. Rejected: Documents-only (no cost sheet during negotiation), editor-only (no archive record).
- **D3 — Free text, auto-paginated.** Custom terms are one big text box with a line-based format (exact rules in the block model below). The document renders as many branded terms pages as needed, each with the signature strip. Rejected: one-page cap (real T&C rarely fit), structured sections editor (slow to paste a legal block a client sent).
- **D4 — Second opinion requested.** The user asked for the independent cold read (routing decision, no scope impact); its output is the Cross-Model Perspective section.
- **D5 — Prefill on switch (adopted from cross-model review).** Flipping Standard → Custom pre-fills the box with the standard terms serialized into the box's own format, so the user edits deltas instead of retyping counsel-approved text. Clearing the box entirely remains allowed.
- **D6 — Approach B: core + operational aids.** Live page count under the terms box, a "Custom terms" badge on proposals that changed the legal text, Excel grouped per phase with a summary block and frozen header row.

## Premises (agreed)

1. The Excel costing file is INTERNAL: filename starts with "Costing", the sheet carries an "Internal costing — not for client distribution" subtitle row, and it never appears among the client-view exports (PPT and PDF stay client-safe).
2. No file bytes are stored: the Excel and the terms pages re-render from proposal data every time, same as today's documents. Consequence (named by the cross-model review): calc.ts is a permanent reproducibility contract — the per-phase totaling gate already established this; every future calc change inherits it.
3. Custom terms are part of the quoted document: stored on the proposal, locked by Mark as sent like every quote field, printed exactly as typed. The user owns the legal wording; the app owns fonts and layout. Standard terms stay the default and English-verbatim.
4. Choosing custom terms replaces BOTH standard pages entirely, everywhere terms appear: the printed PDF pages AND the PPT deck slides. Amended by D5: the box starts pre-filled with the standard text, so "replacement" in practice usually means "standard text with edited clauses", which keeps the counsel-approved wording as the base.

## Cross-Model Perspective

Independent Claude subagent cold read (did not see the session):

- Steelman: these two features turn the app into the system of record for the whole deal — every artifact, client-facing or internal, regenerates from one locked dataset, so numbers and words can never disagree with what was sent.
- Key insight: the Documents-row download means the real job is "answer a question about a deal quoted months ago", which works only because Mark-as-sent freezes data and the calc chain is rounded-canonical.
- Challenged premise 4 (full replacement risks unmaintained forks of counsel-approved text); proposed the prefill mitigation, which the user adopted as D5.
- Engineering guidance adopted: pure buildCostingRows over the existing ProgramTotals; values not formulas in Excel; ONE pure parse+paginate module feeding both the print pages and the PPT slides so the two surfaces can never disagree; fixed line-budget pagination (page geometry is fixed, so it is deterministic and testable).

## Approaches Considered

- **A: Minimal viable** — single-sheet Excel, paginated free-text terms, prefill. Fastest, no operational aids.
- **B: Core + operational aids (CHOSEN)** — A plus live page count under the terms box, "Custom terms" badge, per-phase grouping + summary block + frozen header row in the Excel.
- **C: Full workbench** — multi-tab Excel (tab per phase) and a live side-by-side terms preview. Rejected: preview duplicates Client view one click away; multi-tab adds cost without a stated need.

## Recommended Approach (B)

### Feature 1 — Costing Excel

**New module** `src/features/pricing/costingXlsx.ts` (+ `costingXlsx.test.ts`):
- `buildCostingRows(proposal: Proposal, result: CalcResult): { rows: XlsxCell[][]; boldRows: number[] }` — pure, fully unit-testable (`XlsxCell` stays the existing type in xlsx.ts, untouched; bolding travels as ROW indices, not a cell variant, so `parseXlsxGrid` and the pipeline export are unaffected). The call site passes `boldRows` through to the writer's options. Layout:
  - Rows 1-3, title block: proposal title + client + date + currency; subtitle row "Internal costing — not for client distribution"; blank row.
  - Row 4, the COLUMN HEADER row (bold): Item | Qty | Unit rate | Subtotal. The freeze pane splits BELOW this row (`<sheetViews><sheetView><pane ySplit="4" topLeftCell="A5" state="frozen"/>`), so headers stay visible while scrolling phases.
  - Per phase (in program order): phase name row (bold); one row per cost line under the global headers (label, qty, unit rate, subtotal); phase total cost; effective markup % (`ProgramTotals.effMarkupPct`); phase price (`listShare`); phase margin % (`phaseMarginPct`); days and price/day when set.
  - Summary block: total cost, default markup %, list price, discount (type + amount, flag when clamped), net price, margin amount, margin %, VAT % + amount, total incl. VAT; payment schedule rows (label, %, amount) when the schedule is valid.
  - All money cells are VALUES with the existing money number format (numFmt 167), never formulas — rounded-canonical means the stored number is the truth.
  - Sheet CONTENT is English-only (subtitle, column headers, block labels) — consistent with the internal-record premise and the deck's English-only export decision; only the two UI buttons localize (new i18n key `downloadCosting`, EN + AR, used by both entry points).
- Writer: extend `buildWorkbook` in [xlsx.ts](../../src/features/pricing/xlsx.ts) with an OPTIONAL options parameter `{ boldRows?: number[]; cols?: number[]; freezeRows?: number }` that defaults to today's behavior; `cols` is column widths in Excel character units emitted as a `<cols>` block (the costing sheet passes `[40, 8, 12, 14]`), `freezeRows` freezes that many top rows. `boldRows` applies a bold cellXf to every cell in the listed row indices; boldRows may contain ONLY text-cell rows (one new bold xf with numFmtId 0 would strip the money format from typed cells) and `buildCostingRows` guarantees this — header and phase-name rows are all-text; the bold style is APPENDED after the existing style indices so numFmt ids 165/166/167 keep their positions; the pipeline export call site passes no options and its unit tests must pass unchanged. No new dependencies; JSZip writer already exists.
- Entry points: a Download Excel button in the proposal editor toolbar (enabled for drafts and sent) and a per-row action in [DocumentsList.tsx](../../src/features/pricing/DocumentsList.tsx) next to View costing. Lazy-import like the pipeline export.
- Filename: `Costing - {client} - {title} - {yyyy-mm-dd}.xlsx` via a NEW shared `sanitizeFileName` helper: strip only filesystem-hostile characters (`/ \ : * ? " < > |`), preserve case, spaces, and Arabic; empty client or title falls back to the localized "Untitled" string. This deliberately DIVERGES from the PPT export's ASCII-lowercase slug (`proposalFileName`, which collapses Arabic names to "untitled" by prior decision): the costing file is an internal record and the readable, Arabic-preserving name is the point. Do not change `proposalFileName`.
- NOT in the client view toolbar (premise 1).

### Feature 2 — Custom Terms & Conditions

**Data model** ([types.ts](../../src/features/pricing/types.ts)): `Proposal.customTerms?: string | null` — null/absent = standard terms. `normalizeProposal` coerces non-strings to null. Sent-lock covers the field automatically. Duplicate (V0.x) copies it with the proposal.

**New module** `src/features/pricing/customTerms.ts` (+ tests), the single source of truth for both renderers.

The block model is LINE-based, so parse and serialize are exact inverses:
- `parseCustomTerms(text): TermsBlock[]` where `TermsBlock = { kind: "heading" | "item" | "para"; text: string }`. Normalize CRLF to LF. Each non-blank LINE is one block, checked in THIS order: (1) a line starting with "- " is an **item** (marker stripped, rendered as a `list-disc` bullet exactly like the standard pages) — the item rule runs FIRST so a bullet ending with ":" stays a bullet; (2) otherwise a line of ≤80 chars ending with ":" is a **heading** (displayed as-is, colon retained); (3) anything else is a **para**. Blank lines are separators only and add vertical spacing between a heading's section and the next; consecutive item lines form one visual list.
- `serializeStandardTerms(sections: TermsSection[]): string` — heading line per section with a ":" marker appended only when the heading lacks one, each item as `- {text}`, blank line between sections. Round-trip property (unit-tested, COLON-NORMALIZED): `parseCustomTerms(serializeStandardTerms(TERMS_PAGE_1 + TERMS_PAGE_2))` reproduces every heading (modulo the trailing colon) and every item verbatim, in order. Accepted cosmetic difference, stated on purpose: prefilled headings all display a trailing colon, while the standard pages show colons only where template.ts has them.
- `paginateTerms(blocks): TermsBlock[][]` — deterministic line-budget pagination shared by BOTH renderers. Constants (chars-per-line, lines-per-page) are tuned to the BINDING constraint, which is the PPT text box (4.9in high, smaller than the HTML page's content area), measured against a worst-case fixture (long English clauses, long Arabic clauses, and one long unbroken token), not guessed. Headings cost extra lines and never orphan at a page bottom (a heading whose first following block does not fit moves to the next page).

**Editor UI** (PricingScreen, quote section): a two-option control (existing segmented/toggle pattern) "Standard terms" / "Custom terms". Choosing Custom shows a large textarea (autogrowing, monospace-off, Tajawal in AR) pre-filled via `serializeStandardTerms` when the box is empty. Under the box: live page count "Renders as N pages" computed from the shared paginator. Whitespace-only custom text falls back to standard at render time (never print blank terms pages) with an inline hint. Sent proposals: control and box disabled like every quote field.

**Text direction (Arabic content)**: custom terms may be pasted Arabic legal text. Every rendered block element (HTML) uses `dir="auto"` with `text-align: start`, so each heading/item/paragraph aligns by its own first strong character; the PPT renderer sets per-paragraph `align`/`rtlMode` by the same first-strong-character check (shared helper `isRtlText(text)` in customTerms.ts). The standard pages keep their hardcoded `dir="ltr"` (English-verbatim premise, unchanged). Pagination constants already cover Arabic via the worst-case fixture above. Long unbroken tokens get `overflow-wrap: anywhere` in HTML; the same tokens are in the measurement fixture so the budget covers them in PPT.

**Renderers**:
- [ClientView.tsx](../../src/features/pricing/ClientView.tsx): when custom terms are active, render N `CustomTermsPage` pages (reusing the existing page chrome, legal-English note and signature strip per page) instead of the two `TermsPage` calls. Page title uses a new plural-aware key `docTermsPage` = "Terms and Conditions ({k}/{n})". Standard path is untouched.
- [pptExport.ts](../../src/features/pricing/pptExport.ts): `DeckInput` gains `customTermsPages: TermsBlock[][] | null` (the CALLER runs the shared paginator) and `DeckDict` gains `docTermsPage`; `addCustomTermsSlides` replaces the two `addTermsSlide` calls when custom terms are active, consuming that pre-paginated input. Every block's text MUST be rendered through the existing `splitMixedRuns` helper (pptExport.ts lines 101-126) — it is the guard against the PptxGenJS mixed Arabic+Latin-digit run corruption (upstream #1349) and it is what assigns Tajawal vs the Latin face per run; an Arabic clause containing "30" or "SAR" is the exact corruption pattern. PPT clipping verification: the existing pptx unit-test pattern (JSZip the generated deck, assert the TERMS-slide count equals the paginator's page count — the deck's four non-terms slides are constant — and the LAST block's text appears on the last terms slide) runs on the 1-page, 2-page, and 5-page fixtures, PLUS a mixed Arabic-with-digits fixture; one manual visual open per fixture length before ship.
- The legal-English note (`docLegalEnNote`) is SUPPRESSED on custom terms pages and slides: it asserts the English standard text is authoritative, which is false for negotiated custom terms (and actively wrong over pasted Arabic terms). It keeps rendering on standard pages unchanged.

**One shared predicate**: `hasCustomTerms(p) = p.customTerms != null && p.customTerms.trim() !== ""` in customTerms.ts is the ONLY definition of "custom terms active". Both renderers, the badge, and the legal-note suppression consume it — a cleared box renders standard terms, shows no badge, and suppresses nothing.

**Badge**: neutral StatusBadge "Custom terms" on the proposal switcher row and the Documents row when `hasCustomTerms` is true, so a deal that changed the legal text is visible at a glance.

**i18n**: new keys EN + AR (standardTerms, customTerms, customTermsHint, rendersAsPages plural, customTermsBadge, customTermsEmptyFallback, docTermsPage). Custom text prints as typed (premise 3); UI chrome localizes.

### Explicitly unchanged

Standard terms text, calc chain, pipeline flows, payment schedule, PDF page geometry, client-view export set (PPT + Save as PDF only).

## Tests

- Unit: parse (headings incl. native trailing colon, items, paragraphs, CRLF, blank-line runs), pagination budget boundaries (exactly-full page, heading-orphan push, 1-char overflow), serialize→parse round-trip vs TERMS_PAGE_1/2 (every heading and item, in order), isRtlText detection, item-before-heading precedence (a bullet ending with ":"), buildCostingRows snapshot for a two-phase fixture WITH a per-phase markup override and a discount (the reproducibility tripwire), clamped-discount flag row, filename sanitization fallbacks, pptx slide-count + last-block assertions per fixture length.
- e2e: costing download from editor and from Documents row — unzip, assert the internal-subtitle cell, a cost-line subtotal, phase margin, and grand total match the on-screen figures; custom terms flow — switch to Custom, assert prefilled standard text and page count, edit a clause, open Client view, assert terms pages render the edited clause and page numbering, badge visible, Mark as sent locks the box; EN + AR.
- Playwright overflow assertion: no terms page's content exceeds its page box with a long fixture text.

## Success Criteria

- Open a sent deal from Documents, download the Excel, and every figure matches the app's costing view exactly, including per-phase overrides.
- Paste a real negotiated T&C into the box: the printed pages and the PPT slides show identical pagination and no clipped text at any length tested (1, 2, 5 pages).
- A proposal that never touches the terms control renders bit-identically to today.
- Full DoD: 4 breakpoints × EN/AR, empty/loading/error states, judge-clean, existing suites green.

## Distribution Plan

Existing web deploy (GitHub Pages). Note: main currently carries the per-phase pricing feature held at localhost-stage; the next "publish" ships both together.

## Dependencies

None new. JSZip writer, page chrome, StatusBadge, sent-lock, and i18n plumbing all exist.

## Not in scope

Rich text or markdown in terms, a clause library, Arabic translation of the standard legal text, Excel formulas, multi-tab workbooks, storing generated file bytes, terms in the pipeline table.

## What I noticed about how you think

- You wrote "record it in the documents as excel" — you already think of the Documents tab as the deal archive, and you expect every artifact of a deal to live there. That instinct is what turned this from "an export button" into a system-of-record feature.
- You chose the free-text box over the structured editor without hesitation: you optimize for how the work actually arrives (a legal block pasted from an email), not for how a developer would like it stored.
- When the independent reviewer challenged your replacement premise, you took the prefill fix immediately. Adopting a better idea mid-session without defending the original is faster than most founders manage.
