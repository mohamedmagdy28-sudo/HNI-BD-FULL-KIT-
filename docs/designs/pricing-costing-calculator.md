## Problem Statement

HNI's BD lead builds the financial costing for every client proposal in a fresh Excel file copied from the last one. Rates and formulas drift between copies. The result: costing takes hours to days, margin is a guess until too late, errors have reached or nearly reached clients, and two similar programs get priced differently depending on which file was copied. Build a one-screen pricing and costing tool that produces the financial section of a client-ready proposal.

## Demand Evidence

- The builder is the desperate user: "It's my own pain." They personally build financial proposals and lose real hours each time.
- All four stakes confirmed in one answer: speed (proposals stall on costing), margin (profit is a guess), errors (numbers reached or nearly reached clients), consistency (pricing by file lineage, not policy).
- The consistency answer is the load-bearing evidence: it proves there is no canonical pricing policy, only file inheritance.

## Status Quo

Excel per proposal, each copied from the previous one. Rates are retyped, formulas re-verified by hand, history is scattered across files. The current workflow's one virtue: duplicating the last proposal is fast to start, so the tool must make "duplicate" a first-class action.

## Target User & Narrowest Wedge

- User: the builder themselves (BD lead at HNI, Riyadh, bilingual EN/AR proposals for enterprise L&D clients in KSA/UAE). No personas needed; v1 has exactly one user.
- Wedge (REVISED post-review, user decision): one screen that prices a proposal end to end with manually entered cost lines (no rate card, no price list), and a margin figure trustworthy enough to say out loud to the MD. Saved proposals exist (that is how Duplicate works) but the entire library UI is a switcher in the header; there is no second screen.

## Approaches Considered

### Approach A: One-Screen Calculator (CHOSEN)
Single screen: program-grouped cost table with manually typed lines (rate card dropped post-review by user decision), sticky price/margin panel, print-to-PDF client view. Effort (honest estimate per outside voice T8, reduced by the manual-entry pivot): core screen and calc well under 1 day CC; full Definition of Done (vitest + Playwright coverage, EN/AR at 4 viewports, judge, hni-qa report) roughly 1 more day CC. Prototype/V1 boundary: V1 is the first version used on a real client proposal, and the full DoD applies at that point, not before. Risk: rates half-lived on screen; mitigated by keeping rates a distinct data object (see below).

### Approach B: Pricing Engine (deferred, natural v2)
Separate versioned rate-card feature + proposal workspace + saved proposal list. Deferred for speed to validation; Approach A's data model is designed so B is additive, not a rewrite.

### Approach C: Program Configurator (deferred)
One form describing the engagement generates the full costed proposal. Rejected for v1 because the generation rules are unvalidated against real proposals; revisit after real usage teaches the rules.

## Recommended Approach (as chosen: A, with B's data discipline)

### Data model (REVISED post-review: manual entry, no rate card. TypeScript, all money stored as integer whole SAR; rounded values are canonical per outside voice T2)

- `Settings`: margin floor % (pricing policy, default 30 pending the user's real threshold) and last-export timestamp for the backup reminder.
- `Proposal`: client name, program title, date, currency (SAR fixed in v1), markup % (the canonical stored pricing field; editing target margin writes back the implied markup), discount stored as entered as a tagged value {type: percent | amount, value} (eng review 3A: a percent scales when the price later changes, an amount stays fixed; the summary panel always shows both representations), VAT rate % (default 15; editable per proposal, bounded 0 to 25), payment schedule (list of {label, integer percent}), programs[], `sentAt` timestamp when marked as sent. V1 is SAR-only; UAE/AED deals are explicitly out of scope until multi-currency lands.
- `Program`: name, days, participants, city, costLines[].
- `CostLine`: manual only ({label, qty, unitRate}), typed by the user. No rate references, no RateSet, no snapshot machinery: what you type is what the proposal holds.

### Mark-as-sent (simplified after the manual-entry pivot)

Opening Client view is a consequence-free preview. The explicit "Mark as sent" action locks the proposal read-only: a sent proposal is the durable record of what was quoted and can never change. Any further work on that deal goes through Duplicate, which creates a fresh editable draft revision. With no rate card there is no snapshot to take and no rates-changed hint needed; the lock alone carries the guarantee.

### Calculation chain (single pure function, unit-tested with vitest)

total cost -> list price (from stored markup %; the target-margin input converts to markup on edit; a third input, manual price per day, sets list price = total program days x day rate and also writes back the implied markup, clamped at markup >= 0 and disabled when total days is 0) -> discount -> net price -> margin (computed on net price, excluding VAT) -> VAT on net (per-proposal rate) -> total incl. VAT. Margin panel shows margin in SAR and %, with warning state (semantic warning colors) when below the floor. Also derived: price per participant, shown per program (program's share of net price divided by that program's participants); no cross-program divide, since the same person can attend multiple programs.

Edge cases the pure function must define: total cost of 0 disables the markup/margin inputs until a cost line exists; target margin input is clamped below 100%; a discount may push margin negative, which is allowed but renders the margin block in the danger state; division by zero participants shows a blank per-participant figure, never NaN.

Rounding policy (revised per outside voice T2, rounded-canonical): every derived stage (line subtotals, total cost, list price, discount, net, VAT, total incl. VAT) rounds to whole SAR and all downstream math uses the rounded value. There is no separate precision layer: the number displayed IS the number stored and quoted, so any row a client's finance team recomputes from the displayed figures matches exactly. Payment schedule percents (integers, must sum to 100) apply to the total incl. VAT; installments round to whole SAR except the last, which is total minus the prior installments, so they sum exactly.

Test runner: vitest, dev-only. Three-question justification per CLAUDE.md: (1) problem: the calc chain has arithmetic edge cases that need fast, exhaustive unit tests; (2) why not the current stack: oxlint does not run tests and Playwright E2E is too slow and indirect for pure-function math; (3) maintenance cost: dev dependency only, zero runtime bytes, standard in the Vite ecosystem.

Test scope (eng review 4A, full coverage; revised for manual entry): vitest units for the entire calc chain (discount percent-vs-amount behavior after cost edits, rounded-canonical stage math, payment schedule rounding and sum-to-100, all edge cases), the store (missing key seeding, corrupted JSON recovery, quota failure, export/import round-trip, per-key layout), and Mark-as-sent (sent proposals locked read-only, duplicate creates a fresh editable revision). Playwright specs for the six user flows: price end to end with manual lines, mark-as-sent then duplicate-revision, client view EN and AR with fonts ready and letterhead, schedule validation blocking, switcher open/delete/empty state, reload-mid-edit autosave restore. The existing shell e2e suite must stay green after the App.tsx swap (regression guard). The detailed map lives in the eng-review test plan artifact in ~/.gstack/projects/.

### UI (per approved wireframe)

- Compact header: proposal switcher (shadcn Select listing saved proposals, with delete), proposal meta, sent/draft status badge, actions: Duplicate, Mark as sent, EN/AR toggle, Client view (PDF). Still one screen; the switcher is the entire "library" UI in v1.
- Duplicate semantics: clones every field of the current proposal including cost lines and payment schedule, resets the date to today, appends "(copy)" to the title, and clears `sentAt` so the copy is a fresh editable draft. Duplicate is the primary workflow (it replaces copying the last Excel) and the de facto consistency mechanism now that there is no rate card.
- Main table: cost lines grouped by program; add cost line / add program. Every line is typed manually: label, qty, unit rate.
- Project types (user request, post-v1): each proposal has a projectType selector. "Stand Alone Workshop" (the default) seeds every newly added program with four fixed cost items: trainer daily rate, materials printing, air ticket, accommodation (labels prefilled in the active language, qty 1, rate 0 to be typed). "Custom" seeds one blank line. Switching type affects only programs added afterward; seeded lines stay fully editable and deletable. Proposals stored before the field exist load as "custom". A second project type is expected from the user and slots in as one more union member plus a template list.
- Sticky end-side panel: cost, list price, discount, net price, margin block (the visual anchor), VAT, total incl. VAT, price per participant, payment schedule editor, Client view. Autosave on every change (no Save button, no unsaved-changes dialog).
- Client view: a dedicated in-screen render mode (eng review 2A), not a print-CSS overlay: clicking Client view swaps the screen to only the client document with a Back button; window.print() fires only after document.fonts.ready resolves so Tajawal and brand fonts are guaranteed in the PDF; print-color-adjust set on any tinted cells. Preview is consequence-free for drafts; sent proposals render from their snapshot. The document carries the HNI letterhead header (logo and brand identity per the design system assets) and an @page rule with margins that suppress the browser's default URL/date headers and footers, so the printed PDF is genuinely attachable to a client email (outside voice T7, option B: letterhead PDF; copy-as-formatted-table deferred). Shows only client-facing pricing (no internal costs, no margin), payment schedule, VAT line; EN LTR and AR RTL via the existing global i18n dir switching (eng review 1B: no per-proposal output language field); browser print-to-PDF, no new PDF library. Numbers in both languages use Latin digits with locale-appropriate grouping (Intl.NumberFormat with numberingSystem latn), consistent with financial-table norms.
- Financial Breakdown design, "Ledger" concept (post-v1, chosen from three rendered concepts D18): the page reads as a formal financial instrument. The sections table closes on its own Subtotal row; below it, a numbered payment-schedule table (header ruled 2px black) sits left and the totals ladder right: Discount (hidden when zero), Net investment bold, VAT, then Total including VAT in a solid magenta band with white text, the page's single brand moment (brand rule: magenta punctuates). Rejected alternatives: A executive summary strip (total-first KPI band), C investment-story proportion bars (duplicated the table; degenerates on one-section proposals). print-color-adjust: exact applies to the whole document so the band survives printer background stripping.
- Flexible sections and descriptions (post-v1, user request, direction confirmed D16/D17): each proposal has a free-text "Label sections as" field (empty = localized "Program") that renames group headers, new-group naming, and the client document's first column ("Phase", "Module", ...). Each group has an optional description; the client document shows a true Description column (user's explicit choice over under-the-name rendering) that auto-hides when no group has a description. Legacy stored proposals backfill both fields via normalizeProposal.
- Documents archive (post-v1, user request): a Documents toggle in the header opens the archive of sent proposals (title, client, sent date, total incl. VAT, newest first), with per-row actions to reopen the document (client view, Back returns to the archive) or its read-only costing. Mark-as-sent is the filing action; drafts are not documents. No file bytes stored: a sent proposal is locked, so re-rendering from data reproduces the exact document. Known limit, accepted: if the template design changes later, old proposals re-print in the new template; freezing exact PDF bytes needs real file storage (the Supabase step).
- Client view template (REVISED post-v1, user request): the client document is now a faithful six-page rebuild of the official HNI Financial Proposal template ("Blank Financial Proposal - English.pptx") at its exact 13.33in x 7.5in slide size, so the printed PDF matches a PowerPoint export: (1) cover with the Riyadh-skyline/magenta-arc art, logo, proposal title, "Proposed in {month year}", client name; (2) Financial Breakdown carrying the generated program table, payment schedule, and totals; (3-4) Terms and Conditions verbatim from the template, kept in English in both UI languages (contract wording is never machine-translated; an Arabic note states English governs); (5) HNI bank details table; (6) Thank You back cover. Static template content lives in src/features/pricing/template.ts; cover art at public/brand/proposal-cover.jpg; corner/ring motifs are inline SVG. Page geometry uses physical positioning on purpose: the template art direction does not mirror in Arabic, only text localizes. SECURITY DECISION: the template's embedded real signature and company-stamp images are deliberately excluded because the repo and app are public and those images would enable document forgery; signature blocks render blank for post-print signing. Bank details are included (standard letterhead data) with the public-exposure tradeoff flagged and accepted by the user.

### Storage

`PricingStore` interface: `loadSettings/saveSettings/loadProposals/saveProposal/deleteProposal` + JSON export/import of everything. V1 implementation: localStorage with per-proposal keys (`hni.pricing.v1.proposal.<id>` plus an index key and `hni.pricing.v1.settings`), autosave writes debounced ~300ms (eng review 5A: typing cost stays constant as history grows, and one corrupted key loses one proposal, not the store). Supabase implementation later behind the same interface (premise 5 triggers). Durability nudge (outside voice T4, option B): a dismissible banner reminds weekly to export a JSON backup when the last export is older than 7 days; the app records the last-export timestamp.

### States and validation

- Empty state: no proposal yet shows a one-click "New proposal" with a seeded example. Loading states not applicable (local storage).
- Validation: non-negative qty and rates; discount cannot exceed list price; VAT rate bounded 0 to 25%; payment schedule percents must be non-negative and sum to exactly 100 (inline error, Client view blocked until fixed, schedule defaults to a single 100% line); floor warning is advisory, never blocking.
- Storage errors: every localStorage write is wrapped; on quota or write failure, show a persistent error banner offering JSON export as backup. Corrupted stored JSON on load drops into an error state offering import-from-file recovery instead of crashing.
- Accepted risk (outside voice T5, user decision D28-C): no undo mechanism and no delete confirmation in v1. A mistyped edit autosaves within 300ms and delete is immediate (blast radius is now one proposal, since there is no rate card propagating across drafts). The user explicitly accepted this tradeoff; the weekly export backup is the only recovery path. Revisit if a real incident occurs.
- Import errors: parse failures show what failed and change nothing.

## Success Criteria
