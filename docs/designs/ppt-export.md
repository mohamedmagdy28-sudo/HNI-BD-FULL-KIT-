## Problem Statement

The calculator produces the six-page client proposal as a print-to-PDF. The team's real workflow edits proposal wording in PowerPoint before sending; the PDF cannot be edited, so a full manual rebuild in the old template still happens downstream. Add an Export PPT action that produces a genuinely editable PowerPoint deck matching the official template.

## Demand Evidence and Status Quo

- Q2 answer: "Team edits before sending." The user, their MD, or a BD colleague opens the proposal in PowerPoint and edits scope wording after generation. The PDF's uneditability forces rebuilding in the old template by hand, recreating the exact copy-drift problem the calculator eliminated.
- Sharpest insight of the session (cross-model, adopted): edits target wording, never financials, legal terms, or bank details. Editability is only needed where words live.

## Premises (agreed; premise 1 revised after cross-model challenge)

1. REVISED: editable-where-words-live, faithful-images-everywhere-else. Native editable objects for: cover title/client/date, the complete financial tables including the description column, bank details (IBANs get copy-pasted), the contact line. High-resolution images (2x for crisp projection/print) for: cover art, Terms and Conditions pages, brand motifs, back-cover art. Rationale: freely editable T&C is a liability (silent legal edits), nobody edits terms in a deck, and images sidestep the pptxgenjs mixed-RTL bug on its largest surface.
2. Generation happens fully in the browser with pptxgenjs. Three-question justification: nothing in the stack produces .pptx; a server or paid API would send financial data off the machine (rejected); one runtime dependency, standard and maintained.
3. The deck mirrors the six-page client document, rebuilt in code. Text tagged "Myriad Pro"; PowerPoint substitutes on machines without it, acceptable for an editable working file. No font embedding (pptxgenjs cannot).
4. English export is first-class. Arabic exports behind the same button with a visible "verify in PowerPoint before sending" notice: pptxgenjs has a known mixed Arabic+Latin paragraph bug (gitbrent/PptxGenJS#1349); money in isolated cells and T&C-as-images shrink the surface, but real-PowerPoint verification gates trusting it for delivery. Never ship it silently broken.
5. Signature, stamp, and client logo are injected into the generated deck from browser-local settings as base64 images, same privacy model as the PDF: none of them exist in the public bundle.

## Cross-Model Perspective

Independent Claude subagent cold read: steelman is "the app becomes the source of truth for numbers, PowerPoint stays the collaboration surface"; the deck makes the app's output adoptable by people who never open the app. It challenged uniform editability (accepted, premise 1 revised) and proposed the hybrid slide plan adopted below. Its acceptance test, adopted verbatim: open the output in desktop PowerPoint, click into a description cell, retype it.

## Approaches Considered

### Approach A: Breakdown slide only (rejected for v1)
Single-slide export for deck-merging. CC ~2-3 hrs. Rejected: fails the stated job; the team still rebuilds the other five pages. Its hard part (the table) is built inside B anyway.

### Approach B: Hybrid six-slide deck (CHOSEN)
Full deck via pptxgenjs, hybrid per revised premise 1. CC ~1 day including real-PowerPoint verification.

### Approach C: Real-template XML surgery (rejected)
Fill the official .pptx in-browser via JSZip XML editing. Pixel-perfect masters but fragile against template edits, needs IndexedDB for the ~13MB template, and the highest maintenance cost. Revisit only if pixel-perfect masters become a hard requirement.

## Recommended Approach (B), slide by slide

- Layout: custom 13.33x7.5in (matches the template and the existing print pages). Brand constants from the token values; pptxgenjs hex colors carry no "#".
- Slide 1, Cover: skyline art as background image (pre-rendered 2x PNG asset); native text boxes for proposal title, "Financial Proposal", proposed-in date, client name; HNI logo + client logo (from settings) as images with the divider.
- Slide 2, Financial Breakdown: the whole job lives here. One native table: section label | description (when any exist) | days | participants | unit price/day | investment, subtotal row, then discount/net/VAT rows and the magenta-fill white-bold total band; the numbered payment schedule as a second native table. Column widths matched against the print output. Acceptance test: retype a description cell in desktop PowerPoint.
- Slides 3-4, Terms and Conditions: full-slide 2x images, not native text (tamper-resistant legal copy, Arabic bug sidestepped). ONE English image set, consistent with the parent decision that legal terms stay English in both languages; the Arabic export uses the same images plus the Arabic governs-note rendered into the AR variant. The images exclude the signature/stamp themselves; those are stamped as separate images from settings so the privacy model holds. Their coordinates come from a shared geometry module (the same constants the HTML SignatureBlock uses), the single source of truth for where signatures sit on both surfaces.
- Slide 5, Bank details: native text (copy-paste IBANs), signature/stamp images from settings.
- Slide 6, Thank You: background motifs as image, native contact text.
- Asset pipeline: the T&C and art images are pre-rendered once from the existing client-view pages at 2x (not generated per export); they contain no proposal data and no signature/stamp, so shipping them in the public bundle is safe.
- Arabic: RTL applies ONLY to text runs and table cell alignment (Arabic runs tagged Tajawal, align end); slide geometry stays physical and identical to English, matching the parent decision that the template's art direction never mirrors. Money always in isolated cells with Latin digits. The verify-in-PowerPoint notice appears as a toast on every Arabic export.
- Sent proposals: export is allowed for drafts and sent proposals alike. The app's durable record is the locked proposal inside the app; an exported file, like any file handed to the team, lives outside that guarantee, and producing editable revisions of sent proposals is the feature's purpose.
- States: the Export PPT button shows a generating state while the file assembles and a destructive toast on failure; missing optional assets degrade silently (no client logo drops the cover divider and logo, unset signature/stamp leave the lines blank exactly as the PDF does). Download filename: hni-proposal-{client-or-untitled-slug}-{yyyy-mm-dd}.pptx.
- Tests: Playwright captures the download and verifies the archive Node-side (JSZip, already transitive via pptxgenjs): opens clean, six slides present, slide 1 XML contains the client name, slide 2 XML contains the total; vitest covers the exporter's pure data-mapping helpers. Desktop PowerPoint retype-a-description remains the manual acceptance gate.
- Asset budget and drift control: the pre-rendered 2x PNGs stay under 1.5MB combined; an npm script gen:ppt-assets regenerates them from the client-view pages and is the enforced source of truth, run whenever template.ts legal copy changes (documented next to the script).
- UI: "Export PPT" button in the client-view toolbar next to Print / Save PDF; new strings live under the existing pricing i18n namespace.

## Success Criteria

- Export PPT downloads a .pptx that opens clean (no repair prompt) in desktop PowerPoint.
- A description cell can be clicked into and retyped; the file re-saves without corruption.
- The deck is visually recognizable as the official template at arm's length; numbers match the app exactly.
- Signature, stamp, and client logo appear in the deck on machines where they are set, and are absent from the public bundle.
- The manual rebuild-in-old-template loop ends: the next proposal the team edits starts from an exported deck.
- CLAUDE.md Definition of Done applies: tests, EN+AR runs, judge and QA before "done".

## Dependencies

- New runtime dependency: pptxgenjs (justified in premise 2).
- Pre-rendered 2x images of T&C pages and art (safe for public bundle; no data, no signature).
- No backend, no storage changes.

## Post-Gate Revision (T5 evidence, 2026-08-31, supersedes parts of the amendments above)

The Assignment check found the team DOES edit terms: T&C varies by engagement type (Development Track vs Assessment Center) and Project Assumptions are edited per proposal. Consequences, user-approved (D9: A-then-B):

- Slides 3-4 are NATIVE ENGLISH TEXT, fully editable. The image rationale is void: tamper-resistance contradicts the real workflow, and the Arabic rendering bug does not apply to English paragraphs (legal terms stay English in both languages per the parent decision).
- REMOVED from scope: gen:ppt-assets for T&C, the template-hash manifest vitest (T6.1), and the baked footer (T6.6). The cover embeds the existing proposal-cover.jpg; motifs embed as SVG data URLs. No checked-in generated images remain.
- The native signature strip decision (T3) stands and now simply lives on native slides.
- Arabic deck headings that mix Arabic with Latin digits (e.g. "(1/2)") are emitted as separate text runs to avoid the mixed-run bug.
- Asset injection is parameterized (data URLs passed into the deck builder), so vitest assembles real decks in Node and asserts their XML via jszip: stronger than the E2E-only plan.
- Feature B (terms management in-app: engagement types carry their own T&C variants, assumptions editable per proposal, feeding PDF and PPT) is a separate follow-up feature; the user holds an Assessment Center PDF as source material. Captured in TODOS.md.
- Acceptance gate: desktop PowerPoint availability unconfirmed; the retype-a-cell gate is deferred to before the feature is declared done, not blocking the build.
