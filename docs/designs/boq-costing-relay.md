## Problem Statement

User's words: "1 - Proposals Team: to Build the BOQ which is the cost items for complex projects putting the cost items and costs of it only. 2- Project Manager: revise the BOQ and put the operation cost items of the same project."

Complex projects need a costed Bill of Quantities built by delivery staff before BD prices the deal. Today that happens outside the app (Excel + chat), with no stage tracking, no enforced separation between cost data and margin data, and retyping at the end.

## Decisions (from the session)

- **D1 — Costs only, never pricing.** PT/PM see and edit cost items and cost totals; markup, margin, client price, GP, pipeline, and the client document are invisible to them. Rejected: read-only price visibility (exposes margins to delivery), full access (no compartmentalization).
- **D2 — Assigned handoff with stages.** BOQ draft → PM review → Ready for pricing; one role holds the pen per stage; each handoff is one click. Rejected: open concurrent editing (collisions, WhatsApp turn-taking), standalone-BOQ-then-import-with-no-stages.
- **D3 — BD creates and assigns; assigned-only visibility.** Deals start with BD; a PT/PM account sees only BOQs assigned to it. Rejected: pool visibility, PT-initiated drafts (deferred).
- **D5 — Premise 3 REVISED on the cold read's proof:** field-level locks inside `proposals.data` are impossible to make watertight (RLS cannot redact jsonb on read; per-program markup lives inside the same array elements as cost lines; blob upserts collide). The BOQ is a SEPARATE record; delivery roles get no proposals access at all.
- **D6 — Approach A: full two-role relay.** Rejected: single collapsed costing role (loses the review gate), Excel-template import (no tracking or enforcement — but its import mapping is reused for the BD-side Import step).

## Premises (agreed; 3 revised per D5)

1. Two new roles beside member/manager: `proposals_team`, `project_manager` — one more value each in `profiles.role`, dashboard-granted like today.
2. Costing status is visible to everyone involved; transitions are one click and enforced (not convention).
3. (REVISED) Enforcement by DATA ABSENCE, not field locks: PT/PM can read/write only `boqs` rows assigned to them; they have zero access to `proposals`, so pricing is unreadable by construction — no UI-hiding audit ever needed.
4. Pipeline confidentiality tightening ships in the SAME migration: `pipeline_rows`, `external_deals`, `team_settings` SELECT/UPDATE go from all-authenticated to `is_bd()` (member + manager). Without this, any delivery login reads team GP today.

## Cross-Model Perspective

Independent cold read (did not see the session):
- Steelman: "an approval workflow with information asymmetry, not a collaboration feature" — compartmentalization is the value: delivery staff who never see margins cannot anchor rates or leak GP; BD gets a two-signature cost base.
- Key insight, adopted as the architecture: "one role holds the pen per stage" means BUILD AROUND THE PEN, NOT THE BLOB — turn-taking enforced in the database removes any need for merge machinery.
- Killed premise 3 with a proof (jsonb unredactable on read; normalization round-trip false-rejects; blob last-write-wins collisions) → D5.
- Its 48-hour schema is adopted below essentially verbatim.

## Recommended Approach (A: full two-role relay)

### Schema (supabase/upgrade-boq.sql, one paste like prior upgrades)

The file re-asserts its prerequisites idempotently rather than assuming upgrade-roles.sql ran: drop+re-add the `profiles.role` check constraint with all four values, `create or replace` `is_manager()` and `is_bd()`, and re-create the tightened `proposals_select`. Safe to run on any state of the database.

- `profiles.role` check extends to `('member','manager','proposals_team','project_manager')`. New helper `is_bd()` = role in (member, manager) — SECURITY DEFINER, initplan call form, same pattern as `is_manager()`.
- New table `boqs`:
  - `proposal_id uuid pk references proposals(id) on delete cascade`
  - `owner uuid` (the BD creator), `pt_assignee uuid`, `pm_assignee uuid` (references auth.users)
  - `status text check in ('draft','pm_review','ready','imported') default 'draft'`
  - `context jsonb` — denormalized by BD at creation: proposal title, program names/ids, days, participants, cities. NO client pricing fields, and client name included only at BD's choice (checkbox in the send drawer, default ON).
  - `lines jsonb default '[]'` — `[{id, programId, label, qty, unitRate, origin: 'pt'|'pm', note?}]`
  - `rev int default 0`, `updated_at` — `saveBoqLines` sends `update ... where rev = expected` (compare-and-swap); a zero-row update means the record moved on
- RLS on `boqs`: SELECT for `owner`, managers, `pt_assignee`, `pm_assignee`; UPDATE for owner + assignees ONLY (managers are read-only oversight — granting them UPDATE that the trigger then always rejects would be a contradiction; owner-absent reassignment is a dashboard operation for now); INSERT/DELETE owner-only (`is_bd()` and `owner = auth.uid()`).
- **Pen-holder trigger** (`guard_boq_update`, same proven shape as `guard_pipeline_row_update`): `owner/proposal_id/assignees` immutable except assignees by owner; `lines`/`context` writable ONLY by the pen-holder of the current status (draft → pt_assignee; pm_review → pm_assignee; ready/imported → owner); status transitions restricted (PT: draft→pm_review; PM: pm_review→draft or →ready; owner: any); `rev := rev + 1`, `updated_at := now()` on every update.
- Tightening (premise 4): `pipeline_rows` SELECT+UPDATE, `external_deals` ALL, `team_settings` SELECT+UPDATE → gated on `(select is_bd())`.
- `proposals` INSERT/DELETE and `pipeline_rows` INSERT/DELETE are ALSO gated on `is_bd()` (review catch: SELECT-only tightening left delivery able to INSERT rows, and AuthGate's migration prompt would have pushed a delivery browser's stray localStorage into the team tables). `proposals` SELECT/UPDATE stay as upgrade-roles.sql set them.
- AuthGate routes on ROLE BEFORE the isEmpty/migrate check: delivery roles never see the migration prompt.

### Client

- **Role routing (explicit):** `fetchSnapshot` adds `role` (from the own profiles row) and `boqs` to the parallel fetch; `refreshShared` re-fetches `boqs` too (BD status chips and PT lists stay fresh on tab focus). AuthGate itself branches at the ready phase: delivery roles render `CostingWorkspace` instead of calling `children(store)`; BD roles render the pricing app unchanged. `proposals_team`/`project_manager` accounts get a dedicated **Costing workspace** instead of the pricing app: list of assigned BOQs (status chip, proposal title, due deals first), a BOQ editor, nothing else — no pipeline tab, no documents, no pricing UI exists in their tree. Their session physically never receives pricing data (the API will not serve those rows).
- **Rejected-write UX (the pen moved):** when a BOQ write fails (trigger rejection or rev mismatch — reassignment or status flip under an open editor), the editor re-fetches the row, discards local edits, and shows an "It's not your turn — the BOQ moved to {status}" banner; never a silent generic error.
- **BOQ editor (reuses the cost-table interaction patterns):** per program: cost lines (label, qty, unit cost, line total) + program cost subtotal + grand cost total. Lines added by PM are tagged `origin: 'pm'` and badge "Ops" so BD sees what the PM added. EN/AR, MoneyInput grouping, same tokens. One primary action per stage: PT "Send to PM review", PM "Approve — ready for pricing" or "Return to draft".
- **BD side:** on any own proposal: "Send to costing" drawer — pick PT assignee, pick PM assignee (dropdowns from profiles where role matches), seeds `context` + optionally current cost lines into `lines`. Proposal list shows a costing status chip. At `ready`: "Import BOQ" REPLACES each matched program's costLines wholesale (per-program mapping by `programId`; unmatched lines land in a new program section) — replace, not merge, is the coherent choice under the pen model. Origin tags are DROPPED at import (`CostLine` stays `{id,label,qty,unitRate}`, untouched); the origin distinction lives only in the BOQ record for audit. Sets status `imported`; BD prices exactly as today. Import runs through the existing owner-only save path — one writer per row at every moment; the store's last-write-wins stays safe.
- **SupabaseStore:** snapshot gains `role` and `boqs` (rows visible to me); new methods `saveBoqLines`, `setBoqStatus`, `createBoq`, `importBoq` — all through the existing per-record write queues. localStorage mode: no BOQ feature (cloud-only, like accounts).
- i18n EN/AR for every new string; RTL first-class as always.

### Tests

- Unit: line mapping on import (by programId, replace-per-matched-program, unmatched → new section, origin tags dropped), context seeding strips pricing fields, role routing.
- SQL adversarial (manual checklist in the doc, run once with test accounts): PT reads `proposals` → zero rows; PT reads `pipeline_rows` → zero rows; PT updates `lines` at status `pm_review` → rejected; PM flips status draft→ready skipping review → rejected; owner reassigns mid-flight → allowed; deleted proposal cascades its BOQ.
- e2e: localStorage suites unchanged and green (feature is cloud-gated).

## Not in scope

- PT-initiated BOQs (deferred; D3), pool visibility, more than one PT/PM per BOQ.
- BOQ version history beyond origin tags + rev counter; comments/chat on a BOQ; notifications (status chip + tab-focus refresh only).
- Rate-card integration (TODOS rate card v2 becomes MORE valuable after this ships — delivery typing rates is the drift source; noted, not built).
- Realtime presence; concurrent co-editing (the pen model makes it unnecessary).
- Client name hiding beyond the send-drawer checkbox.

## Success Criteria

- A proposals_team test account: sees ONLY its assigned BOQs; `select * from proposals` and `select * from pipeline_rows` from its session return zero rows (the D1 database proof).
- Full relay on one real deal: BD sends to costing → PT builds lines → PM adds ops lines (badged) → ready → BD imports → per-phase pricing on the imported costs → sent. Cost totals identical between the BOQ view and the proposal after import.
- An out-of-turn write (PT editing during pm_review) is rejected by the database, not just the UI.
- Existing suites fully green; Magdy/Heba/Vandana/Menna experience zero change until they touch the new flow.

## Distribution Plan

Existing web deploy + one SQL paste (`supabase/upgrade-boq.sql`) in the dashboard; new delivery accounts created the same way as today (user + profiles row with the new role values).

## The Assignment

Before the build: take ONE real complex project you priced recently and write its BOQ as a plain list (item, qty, unit cost, who would have entered it — PT or PM). That list becomes the acceptance fixture, and it will answer the two questions the design left open: whether PT needs per-diem-style rate helpers, and how many lines a real BOQ carries (which sizes the editor's UX).
